# Shared history editorial workflow

## Astra ownership — Denny's instruction, 14 September 2026

GPT-6 Astra (`gpt-6-astra`) must explicitly handle historical research, source assessment, fact-checking and factual article writing. A coordinating or publishing agent may maintain the calendar, validate metadata and publish specifically approved articles, but must not substitute another model for this research or writing.

Use a runtime-confirmed Astra session or explicitly delegate the research and writing to an Astra worker with model `gpt-6-astra` where supported. This instruction authorises that delegation. A prompt saying “act as Astra” is not model selection. If Astra execution cannot be selected or verified, stop research/writing and report the model-routing blocker; do not silently fall back. Record the actual configured model and available run/worker identifier in editorial notes, never invent them or put them in public prose. Preserve existing completed drafts without relabelling their authorship. Denny's article approval and all shared-calendar, source and publication rules still apply.

The only commissioning calendar is [`docs/editorial/history-calendar.json`](https://github.com/DennyRegan/the-liverpool-brief/blob/main/docs/editorial/history-calendar.json) on **main** in `DennyRegan/the-liverpool-brief`. It records event/date, featured Monday, selection, writing status, ownership, real draft path and published destination. This guide is a protocol, not a second list.

## Activation and access

The setup review branch is a proposal, not an active competing calendar. Activate only when the calendar and this guidance are approved and merged to main. The weekly automation must stop if it cannot fetch the latest main calendar or if that file is absent. Never fall back to a private checkout, chat list, old planner or a newly invented calendar. The review PR and weekly task point to the same canonical URL. Approving this workflow does **not** approve any article or site release.

## Read, claim, save, reconcile

1. Fetch origin/main and read the latest calendar, AGENTS.md, docs/this-week.md, docs/connected-history.md, docs/seasons-publishing.md, schemas and entity registry. Inspect published content, the recorded drafts and open branches/PRs for the same exact historical event. Preserve the current week plus three following full UK calendar weeks. Fill the nearest genuine writing gaps first; no filler or fixed number of stories per day.
2. Use the existing row. Register a worthwhile new proposal here before work begins. `selected` preserves an existing selection; `provisional` needs research/selection review; `alternative` is not a replacement or an instruction to draft. A saved alternative must not be rewritten. Select alternatives only with an explicit reason recorded in the row, preserving the displaced item.
3. **Claim before drafting:** set `status: writing`, a unique `owner` (editor/task plus run identifier) and `claim: { token, claimedAt, baseCommit }`. Save this claim to the authoritative main calendar and confirm it is visible remotely before writing. Use a small editorial-only commit under the approved workflow, never a site/content publication commit. If main protection requires review, submit the claim for review and stop that item until accepted. A claim only on a private or unmerged branch does not reserve work.
4. After fetching again, confirm nobody else owns the row. Never take another writer's claim, even if old; record a blocker and continue to another unclaimed genuine gap. The completed six reports for 14–19 September 2026 are already written and await Denny's review: do not reclaim, rewrite or publish them. Silence is not approval.
5. Save each complete factual draft immediately under `docs/editorial/drafts/`, outside the published content loaders, with its sources and editorial evidence notes. Set the real `draftPath`, `status: ready_for_review`, retain the owner, and clear the claim. Checkpoint partial work with its real path and keep `writing` status. Save draft and calendar update together. Continue to the next claimed gap without waiting for the previous article's approval.
6. Before **every** shared save, fetch again and reconcile changes by row ID against the latest main SHA. Use a normal fast-forward push (or compare-and-swap API update with the expected SHA), never force-push. If rejected, reread, preserve other writers' rows and drafts, reapply only your changes and rerun checks. For the same-row conflict, stop rather than overwrite. A reviewed PR must be refreshed against main immediately before merge. Confirm the saved remote claim/status after success.
7. Record explicit article approval in `approval: { by: "Denny", recordedAt, evidence }` and only then use `approved`. Keep unknown approval null. `published` is an observed existing destination or a separately approved publication, not something inferred from a draft's metadata. Set new publication dates only at publication; verify the live destination before changing status to published.

## Editorial and metadata rules

Requested **factual** match reports, transfers, appointments and biographies may be drafted by editors/AI. Opinion remains Denny's writing; preserve his wording and all existing writers' work. The withdrawn original AI Archive articles stay withdrawn. This supersedes older blanket prohibitions on requested factual drafts and separate supporting-article/planner queues. Old longlists and progress files are provenance only; reconcile their overlapping items here before commissioning anything.

Use British English and text only: no illustrations or image workflows. Retrieve the actual sources before asserting historical facts, prioritising club/competition records and reliable contemporary or historical reporting. Cross-check significant facts independently where possible. Do not invent dates, quotes, action, motives or sources. Record conflicts and omit unresolved claims. Each retrieved source needs a High/Medium/Low confidence label and claim scope in **editorial notes**, never the article's public prose. Mark unretrieved claims UNVERIFIED. Group article sources at the bottom; do not repeat inline sources after every paragraph or publish duplicate source lists.

Keep `historicalEventDate` as the exact historical date, `date` as actual publication date, principal `season` as consecutive `YYYY-YY`, slug matching the canonical filename, and only genuine existing or validated new entity IDs. Follow the current schemas, not old drafts blindly. Factual classification in a review draft is **not approval**. After Denny approves publication, use the existing `content/archive/liverpool/<slug>.md` and `/archive/<slug>` destination, classified appropriately for History. Never create a second article store or new article URL scheme. Existing published but unclassified articles need Denny's approval before factual reclassification.

No new article may be published, merged or deployed without specific approval. The weekly task prepares drafts and calendar updates; it does not ship application/layout changes. Source-verified short-event maintenance may use existing content-only authority, but cannot publish a new article or silently approve a classification change. Keep new event links pointed only at real published destinations. If the display changes need review, keep that separate and report its state honestly.
